Volatility Factor Project
¶

Overview: the Volatility Factor project is comprised of several python modules (dot.py files), a configuration file (dot.YML) for user-provided configurations and arguments, and input data (dot.csv file). To 'operationalize' the project for production use, where users not proficient in Python may be required to generate output, we designed the project to limit user-interaction with the code by restricting the entry-point to the configuration file. The configuration file works like a text-base user-interface - users can change arguments for relevant parameters to generate the desired output. Once the user has set the arguments in the configuration file, a single runner script (volatility_factor_main.ipynb) is executed to generate the output. This script imports other internally developed modules and third-party packages required to generate the desired output. Please refer to GARCH Simulation - Volatility Factor - MDA Departmental Procedures for operating procedures and GARCH Simulation - Technical Documentation for technical details.

Purpose: the purpose of this document is to describe and provide illustrative examples of the functionality within the modules. By design, both the project and model were constructed to be both flexible and extenable; as such, it's not feasible to discuss every permutation or available use-case. However, this will provide an overview of general functionality and focus on it's use to estimate the FHLBank's Volatility Factor. Note: this document is NOT procedural (it does not cover how users will generate the output for production use). See GARCH Simulation - Volatility Factor - MDA Departmental Procedures for operating procedures.

Componets: the project is primarily comprised of the following componets, which are described in greater detail herein.

1. VaRData.py: this module contains the VaRData class. It provides various measures and/or descriptive attributes for the index pricing. All critical inherit from the VaRData class.

2. VarMethods.py: this module contains the GarchSim class which encapsulates the required data and methods required to by the model to estimate the Volatility Factor.

3. VaRBacktesting.py: this module contains the VarBacktest class with methods to calculate various backtesting measures and plots.

4. constants.py: this module will contain contants for use in other modules. Currently, only a single object is created in this module (CONFIGS).

5. util_functions.py: this module encapsulates helper functions used in the runner script, volatility_factor_main.ipynb. For instance, it contains a function to create a list of sample periods which can be used for iteration.

VaRData
¶

Description: this module reads the index pricing data (pricing_data_combined.csv) and assigns the resulting dataframe to a global variable DATA. These data are used in the VaRData class to compute measures and/or descriptive attributes of the index prices (via cached properties). These properties generally fall into one of two categories:

1. price measures: prices, price returns, log returns, etcetera. These measures are calculated from the data in pricing_data_combined.csv (DATA).

2. descriptors: ticker description, pricing index description, etcetera. These attributes are sourced from either the pricing_dat_combined.csv or the var_config_volfactor.yml (CONFIGS).

VarMethods
¶

Description: this module contains the GarchSim class used to estimate the Volatility Factor. There are two primary componets used to calculate the volatility factor using the methods available in this class: (1) estimation of the model; and (2) simulation processes.

Estimation: we use a third-party package ARCH to estimate the GARCH (1,1) model. All of the simulation methods within the class are dependent on various objects and attributes of classes created when fitting the model. As such, we persist all of the required data (and the .fit object itself) as pseudo read-only properties for access in when the simulation methods are called.


Below we provide some examples to illustrate some features of this class on a stand-alone basis.

Simulation
¶

Once the model is specified and fit using the Arch package, a simulation processes generates forward-looking one-day price paths. The one-day price paths are then transformed to n-day price change paths as setforth in the model documentation. The purpose of this section is to outline some of the different types of simulations the model was designed to accomodate. These simulations are invoked by passing one of the following arguments to the shock_type parameter of the CustomNDayPriceSimulation method.

1. normal: this simulation process draws the exogenous shocks from a standard normal distribution for the entire duraction of the forecast (horizon 1 + horizon 2 + ndays - 1).

2. custom_normal: this is the simulation process used to derive the long-term VaR - the volatility factor used for the annual review period</b>. It is idential to the "Normal" simulation - it draws the exogenous shocks from a standard normal distribution for the entire duration of the forecast. However, we impose stress to the shocks for periods 64 through 68 by by multiplying them by $\sqrt{2}$. This process is described in detail in section 3.3.1 of the GARCH Simulation - Technical Documentation.

3. bootstrap: Unlike the simulation processes described above - both of which assume $e_t$ follow a standard norml distribution - this process draws from the fitted values of $e_t$ from a user-defined date range. When shock_type is set to bootstrap, users must provide two additional arguments to the bootstrap_start and the bootstrap_end parameters.

4. custom_bootstrap: This simulation process combines the normal and the bootstrap simulation processes described above. For the first horizon1 periods, shocks are drawn from the fitted values of $e_t$ from a user-defined date range passed to the bootstrap_start and the bootstrap_end parameters, and for the remainder of the simulation, the the shocks are drawn from a standard normal distribution.

Simulation - Starting Values
¶

All of the different simulation types described above can be executed without setting the starting values of $ϵ_0$ and $α_0$. When the start_vals parameter is unchanged from it's default value of None, the last fitted values for ϵ and α are used in the simulation. To specify the starting values, a two-element list must be passed to the start_vals parameter; the first element with a date and the second element with a quantile. When a user provides values for the start_vals parameter, a one-day variance forecast is performed for each business day from the date provided through the end of the sample period. The values of $ϵ_0$ and $α_0$ are set to the corresponding quantile of the series of one-day variance forecasts. For the long-term VaR - the volatility factor used for the annual review period - the values of $ϵ_0$ and $α_0$ are set to the 50th quantile of the one-day variance forecast over the last year in the sampele period.</b>.
